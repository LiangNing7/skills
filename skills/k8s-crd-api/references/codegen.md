# Code generation

## Hand-written vs generated

| File | Owner |
|---|---|
| `doc.go`, `register.go`, `<kind>_types.go`, `<kind>_phase_types.go`, condition/common types, `defaults.go`, `validation/`, `install/`, group-level `<group>/OWNERS`, `fuzzer/`, API tests | **hand-written (you write)** |
| `zz_generated.deepcopy.go` | `deepcopy-gen` |
| `zz_generated.conversion.go` | `conversion-gen` |
| `zz_generated.defaults.go` | `defaulter-gen` |
| `types_swagger_doc_generated.go` | repository Swagger-doc generator |
| `generated.pb.go` / `generated.proto` | protobuf generator |
| clientset / listers / informers | `client-gen` / `lister-gen` / `informer-gen` |
| applyconfigurations | `applyconfiguration-gen` |

Generators emit mechanical boilerplate. Anything with business semantics
(types, defaults, validation, or a required semantic conversion) is
hand-written. Never edit a `zz_generated.*`, `generated.pb.go`,
`generated.proto`, or `types_swagger_doc_generated.go` file by hand.

## doc.go markers drive generation

Internal:

```
// +k8s:deepcopy-gen=package
// +groupName=<group>
```

External:

```
// +k8s:openapi-gen=true
// +k8s:deepcopy-gen=package
// +k8s:protobuf-gen=package
// +k8s:conversion-gen=<internal pkg>
// +k8s:conversion-gen-external-types=<this pkg>
// +k8s:defaulter-gen=TypeMeta
// +groupName=<group>
```

For an existing group, copy additional peer conversion and defaulter-input
markers from its `doc.go`; they are repository-specific and affect conversion
of imported Kubernetes types.

## Common generator arguments

| Argument | Meaning |
|---|---|
| `--go-header-file <boilerplate>` | copyright header template |
| `--bounding-dirs` | deepcopy boundary (avoid generating external packages) |
| `--output-pkg` / `--output-dir` | client/lister/informer output (e.g. `pkg/generated/...`) |
| `--plural-exceptions` | irregular plural resource names |
| `--extra-peer-dirs` | conversion peers for cross-package types |

Most `zz_generated.*` files have an autogenerated build tag and generated-code
header. Protobuf and Swagger-doc outputs use their own headers. Treat the
filename and generated notice as authoritative; `verify-codegen` enforces that
committed output matches a fresh run.

## Execution strategy

1. Detect a repo script (`scripts/update-codegen.sh`, a `Makefile` target, or
   `hack/`). Inspect its supported targets before running it.
2. Prefer focused targets that update API-package artifacts only, for example:

```bash
scripts/update-codegen.sh protobuf deepcopy swagger defaults conversions
```

   Read the target names from the repository's own codegen script; the example
   above is illustrative, not authoritative.

   Do not run client/lister/informer/applyconfiguration or repository-wide
   OpenAPI targets when that would write outside `pkg/apis/**` unless the user
   explicitly expands the scope.
3. If there is no repository wrapper, derive commands from the versions of the
   installed generators (`--help`) rather than copying flags from another
   release; gengo CLI arguments vary by version.
4. Run `gofmt`, focused tests, and the repository's `verify-codegen` command.
